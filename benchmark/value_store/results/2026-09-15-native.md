# Native JIT and AOT comparison — September 15, 2026

The existing store/document optimizations retain substantial gains in native
release AOT. The traversal experiments also show why JIT alone is insufficient:
callback and lazy iteration are approximately tied for a simple sum in JIT, but
the lazy iterator takes about twice as long in AOT. Its overhead is much smaller
in the cleanup model, where more time goes into useful work per element.

[Raw samples, provenance and command receipts](2026-09-15-native.json) accompany
this report. No production traversal API was added as part of this comparison.

## Method and evidence boundary

- Flutter 3.44.4 / Dart 3.12.2; macOS 26.2, arm64, 10 logical CPUs.
- Real Flutter desktop applications importing the actual Loon library. Debug
  supplies the JIT series; release supplies the AOT series. They are kept separate.
- HEAD `898852c59fad1fc51ee631a4763f62b932475d6f` plus the working changes recorded
  by file hashes. Hosted package versions were pinned to the root lockfile.
- Two variants × two compilation modes × five suites × two fresh-process passes:
  **40 timing processes and 728 operation-result rows**. Each row contains nine
  measured samples; each reported operation pools 18 samples across two processes.
- At least five warmup iterations and 250 ms of warmup phase time before samples.
  That phase includes fixture setup/checks and does not prove JIT optimization has
  completely settled. Job order and iterable/extraction method order were reversed
  in the second pass. All builds and validation completed before timing started.
- Fixtures and correctness checks are outside timed intervals. Registration has
  its own explicitly timed metric. Release checks throw exceptions rather than
  relying on disabled assertions. Fake timers drain actual Loon work; results
  describe CPU processing, not real event-loop latency or frame smoothness.
- Unrelated host activity was present. Treat small differences as inconclusive;
  the broad dependency gains appeared in both process passes. The full data gives
  process medians and load averages. Their range is not a confidence interval.
- This is desktop evidence. Physical mobile execution and retained Dart heap /
  allocation measurements remain separate qualification steps. Whole-process RSS
  is diagnostic context only.

Original command, retained as provenance (the Python runner has since been
replaced by the Dart workflow in [the README](../README.md)). This run used nine
trials; the workflow defaults to 15:

```sh
python3 benchmark/value_store/run.py \
  --out build/value_store_profiles/20260915-native-final \
  --variants baseline,combined \
  --suites lookup,traversal,iterable,extraction,dependency \
  --trials 9 --warmups 5 --warmup-ms 250 --passes 2
```

Use `dart run benchmark/value_store/run.dart` with the same options for a current
comparison and choose a new output directory. Current variants include later
optimizations; use the archived hashes when interpreting the historical numbers.

## Existing production changes

`baseline` already includes retained dependency documents and `extractValues`.
`combined` additionally includes the empty-store guards, incremental path parsing
for `get`, and cached document path/hash. This comparison does not measure the
entire change from the original PR and does not isolate the individual changes.

Native release AOT, pooled median milliseconds:

| Workload | Baseline | Current | Time reduction |
| --- | ---: | ---: | ---: |
| Update one source with 100k dependents | 153.788 | 73.018 | 53% |
| Delete the 100k dependent documents | 42.673 | 22.594 | 47% |
| Update + deliver to four queries over 10k dependents | 50.303 | 24.218 | 52% |
| Update one source affecting 1k of 100k documents | 1.403 | 0.637 | 55% |

For the first row, the separate process medians were 145.921–158.232 ms at baseline
and 72.910–73.125 ms with the current code. For deletion they were 40.057–44.488 ms
and 22.399–22.815 ms respectively. These gains are larger than the observed
between-process variation.

## Callback, lazy iteration and eager extraction

Current library, pooled median milliseconds:

| Workload | Mode | Callback | Lazy iterable | `extractValues` |
| --- | --- | ---: | ---: | ---: |
| Sum 100k values | JIT | 0.888 | 0.867 | 4.215 |
| Sum 100k values | AOT | 1.340 | 2.748 | 5.008 |
| Cleanup model, 100k entries | JIT | 19.405 | 21.380 | 29.169 |
| Cleanup model, 100k entries | AOT | 19.036 | 19.691 | 24.857 |

The lazy prototype uses delegated bucket iterators (`yield*`). In AOT its simple
sum takes about 2.05× the callback time. In the cleanup model it is about 3.4%
slower than the callback and 21% faster than eager extraction. The cleanup model
is isolated forward/reverse index work; it is not a replacement measurement for
the whole Loon deletion operation above.

This supports offering a conventional lazy iterable for callers that do not need
a materialized set. It does not establish that callback overhead is irrelevant
or that every hot caller should use an iterable. The public API decision can
remain separate from the implementation of specialized eager extraction.

## Should extraction simply call the lazy API and `toSet()`?

Current library, root extraction of 100k stored values, native release AOT ms:

| Values | Current extraction | Direct lazy → set | Shared buckets → set via `addAll` | Shared bucket lazy → set |
| --- | ---: | ---: | ---: | ---: |
| Unique integers | 4.094 | 5.540 | 4.034 | 5.032 |
| Identity entry objects | 7.252 | 8.722 | 7.029 | 8.445 |
| Repeated values, 100 distinct | 1.628 | 3.241 | 1.681 | 2.770 |

Keep the efficient eager extraction path. The private shared-bucket prototype
approximately preserves its performance while allowing a lazy public iterator to
reuse tree navigation. Tiny differences within that pair are not established
wins. Simply implementing extraction as `valuesUnder(path).toSet()` adds material
overhead here, especially with repeated values. Shared-bucket lazy aggregation
and cleanup still need their own comparison before adopting that implementation
for those callers. ValueRefStore's cached distinct-value index is a separate
extraction fast path and was not replaced.
