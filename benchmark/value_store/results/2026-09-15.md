# ValueStore: first profiling round

September 15, 2026. [Raw samples, manifests and receipts](2026-09-15.json). [Suite and reproduction](../README.md).

## Applied changes

- Exact get walks path segments incrementally and returns immediately for an empty store.
- ValueStore and ValueRefStore skip non-root deletion work when empty. Root deletion still detaches the backing map, preserving existing alias behavior.
- Document caches its immutable path and hash per handle.
- Existing retained dependency entries plus extractValues remain the baseline for this round.
- Dedicated touch, direct visitor and collection-map reuse remain experiments/demos.

## Is the tree a good fit?

Yes for Loon's combination of collection reads, ancestor checks and subtree operations. Exact point lookup alone favors a flat map. These measurements use prebuilt input paths for both implementations; the flat map can reuse full-string hashes while the tree still parses and hashes path segments.

| Operation | ValueStore | Flat map |
| --- | ---: | ---: |
| 100k deep point reads | 53.6860 | 2.7865 |
| Read one 1k-value collection among 100k values | 0.1470 | 1.4910 |
| Remove one 1k-value subtree among 100k values | 0.0020 | 5.1925 |

Subtree deletion is near timer resolution and includes a post-delete existence check. This measures detaching ValueStore data; deleting Loon documents also requires reverse-dependency cleanup. A flat map needs an additional index to avoid scanning unrelated entries for hierarchy operations. Keep the tree and improve how batch operations access its existing nodes before adding another persistent index.

## Is the dedicated touch path worth separate code?

It helps the largest isolated fan-out, but its benefit is not uniform. In the broader repeat, four queries over 10k dependents measured combined versus touch:

| Operation | Combined | Touch helper |
| --- | ---: | ---: |
| Write plus stream delivery | 26.95 | 29.33 |
| Ten writes before delivery | 22.92 | 23.56 |

These variations do not establish a universal regression or gain. Recommendation: fold the redundant-event-check removal into scoped collection-map reuse rather than adding a separate production touch path now.

## Visitor use cases

The callback visits every stored value at/below a path. The unique-value aggregation uses one distinct Row per stored entry, making extractValues and a visitor equivalent.

| Workload | Existing approach | Visitor |
| --- | ---: | ---: |
| Sum 100k unique values | 7.9065 | 1.2405 |
| Export 100k values into a list | 27.0530 | 3.1250 |
| Sum a 1k-value subtree, compared with repeated get | 0.2170 | 0.0100 |
| Count all 100k stored values, including duplicates | 24.2110 | 0.9230 |
| Read 1k immediate collection values | 0.0140 | 0.0160 |
| Read ten known IDs among 100k values | 0.0020 | 2.4195 |
| Collect distinct values from 100k repeated values | 1.7795 | 2.4760 |

A visitor is useful for subtree-wide aggregation, exports and cleanup. It should not replace sparse exact reads, immediate child reads, or deduplication indiscriminately. Candidate library uses include dependency-entry cleanup and accumulating recursive dependents directly into one result set. Persistence paths that need full path keys still need a path-aware operation. No visitor API has been added to the library.

## Where collection-map reuse belongs

Inside BroadcastManager dependency propagation. An account update touches its transactions, which can touch a shared summary. Resolve the reverse and pending-event maps of each collection once and access document IDs within those maps. Keep the maps only for this synchronous traversal; do not retain them across deletion or clear.

[Runnable demo](../collection_lookup_demo_test.dart) covers a shared summary, pending events, a cycle, and reuse after clearing the event store. It uses existing ValueStore APIs and creates the first event bucket with a normal path write.

Grouped reverse lookups during deletion are related but separate: many transactions sharing an account let the operation resolve that account's dependent set once, remove each transaction, then prune the empty set. Unique dependencies offer no lookup reuse.

## Validation and evidence limits

- Final working tree: 125 core tests plus the runnable collection demo passed; targeted analysis found no issues, and git diff --check passed.
- Visitor semantics and all timed results have correctness assertions. Temporary touch and visitor library variants also passed their copied core suites.
- Final profiles: two processes per variant, three warmups and seven measured trials each. Broad repeat: two processes, three warmups and five measured trials each.
- An initial broad pass suffered interference from unrelated Dart work. It was excluded; the repeat and focused final run are archived here. Process-to-process variation remains visible in the raw samples.
- macOS arm64, Dart 3.12.2, Flutter test/JIT. No release/device performance claim. Retained memory, allocation bytes and CPU sampling were not measured.
- The final source hashes match the working library at report generation. The broader repeat preceded the root-deletion alias-preservation adjustment; its own source hashes are archived separately.
